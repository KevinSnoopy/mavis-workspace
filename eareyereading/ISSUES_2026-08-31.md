## 2. 内置语音引擎：解压时文件数量统计的预扫分母 bug

### 现象
- 解压 Piper 归档时，进度条可能永远到不了 100%，停滞在 99.x%。
- 体感：解压阶段进度条长时间不动，用户误以为卡死。

### 根因
- 文件：`app/src/main/java/com/eareyereading/tts/EmbeddedTtsEngine.kt`
- 两个函数对"什么算 entry"的口径不一致：
  - `countTarEntries`（851-868 行，预扫）：**所有 entry 都 +1**（不区分 file/dir/其他类型）
  - 解压循环（1007-1012 行）：**只数 `entry.isFile || entry.isDirectory`**，跳过 symlink/fifo 等
- 后果：归档里如果包含 symlink（实际 Piper 的 `espeak-ng-data/phonindex` 等就是 symlink），
  分母（预扫）> 分子（解压），进度永远到不了 1.0。

### 期望行为
- 预扫与解压循环用同一套过滤条件，统计口径一致。
- 建议抽一个 `shouldCountTarEntry(entry, canonicalRoot): Boolean`，
  两个调用点共用，分母分子口径永远一致。

### 详细分析（5 条子 bug）

#### Bug 1（P0，必修）：预扫 / 解压循环过滤口径不一致 → 进度卡 99%

**预扫** (`countTarEntries`, 851-868 行)：
```kotlin
private fun countTarEntries(tarballFile: File): Int {
    var count = 0
    try {
        java.io.FileInputStream(tarballFile).use { fis ->
            BZip2CompressorInputStream(fis).use { bzis ->
                TarArchiveInputStream(bzis).use { tis ->
                    while (tis.nextEntry != null) {
                        count++   // 不分类型，所有 entry 都 +1
                    }
                }
            }
        }
    } catch (e: Exception) { ... return -1 }
    return count
}
```

**解压循环** (1007-1012 行)：
```kotlin
if ((!entry.isFile && !entry.isDirectory) ||
    !File(modelsDir, name).canonicalPath.startsWith(canonicalRoot)
) {
    entry = tis.nextEntry
    continue    // 跳过，非 file/dir 不计入 extractedEntries
}
extractedEntries++
```

**口径差异**：
- 预扫：所有 entry 都 +1（symlink、fifo、char device 等都算）
- 解压：只数 `entry.isFile || entry.isDirectory`，其他类型不计入分子

**后果**：
归档里夹 symlink 时（**实际 Piper `espeak-ng-data/phonindex` 就是指向 `phondata` 的 symlink**），
分母（预扫）> 分子（解压），**进度条永远到不了 1.0**，UI 永远停在 412/415 的 99%。

**修法（推荐）**：抽一个私有函数 `shouldCountTarEntry(entry: TarArchiveEntry, canonicalRoot: String): Boolean`，
把过滤条件集中，预扫跟解压循环都调它，分母分子永远一致。

---

#### Bug 2（P2）：预扫无路径校验（与 Bug 1 配对出现）

`countTarEntries` 没有参数 `modelsDir`，**根本没法做 path traversal 校验**。
解压循环里有的 `canonicalPath.startsWith(canonicalRoot)` 检查，在预扫里**不存在**。

不算安全漏洞（解压那一步是守得住的），但跟 Bug 1 是同一类问题：
不安全的归档里 path traversal 条目**被数到分母、但解压时跳过**，
进一步放大 Bug 1 的进度卡死。

**修法**：把 `modelsDir` 传给 `countTarEntries`，或者抽到工具函数里复用同一个 root 路径。

---

#### Bug 3（P2）：目录条目计入"文件数"，UI 体感偏差

tar 解压常见形态：先一条 `dir entry`（`isDirectory=true`），再零到多条 `file entry` 在它下面。
代码里不管 `isFile` 还是 `isDirectory`，都 `extractedEntries++`（1047 行）。

**用户感知偏差**：
- 预扫得「N 个 entry」 → UI 显示"解压中 100/412" = 24.3%
- 实际 100 个里有 30 个是空目录、70 个是文件
- 再解压 300 个文件，体感上"卡 1/4"那一会儿实际是空目录扫得快，**并不是真的"解压 1/4"**

**修法**：要么只数 `isFile`（贴近"解压文件数"），要么 UI 文案说清楚"包含目录"。
**建议只数 `isFile`**：目录条目通常很短（mkdirs() 一行），
用户对"我刚才在解压 412 个文件"更有耐心，体感更连贯。

---

#### Bug 4（P1）：预扫失败时末态分子分母差 1，UI 不收敛

967-970 行动态分母兜底：
```kotlin
if (preCountedEntries <= 0 && extractedEntries >= totalEntries) {
    totalEntries = extractedEntries + 1
}
```

`pushExtractionProgress` 里每次调用都判断 `extractedEntries >= totalEntries` → 分母 +1。
下一个 entry 解出来 `extractedEntries++` 后**再次**满足条件，分母又 +1。
只要解压还在继续，分母永远比分子大 1 —— 这是设计意图（保持单调前进），没问题。

**但末态不收敛**：解压完最后一条 entry 后，`extractedEntries` 和 `totalEntries` 可能差 1，
UI 永远停在 `412/413` 而不是 `412/412`（在预扫失败路径上）。
下面 1051 行 `pushExtractionProgress(isFinal=true)` 之后没再调 `extractedEntries++`，
**也没把分子推到分母**。

**修法**（1051 行附近）：
```kotlin
pushExtractionProgress(isFinal = true)
// 补一句：预扫失败路径末态对齐
if (preCountedEntries <= 0) {
    _downloadProgress.value = Progress.Extracting(
        extractedEntries, extractedEntries, lastExtractionEntry,
    )
}
```
或者直接把末态的 `extractedEntries / totalEntries` 分子分母都设成一样的值。

---

#### Bug 5（P3）：异常态 UX 跳变

解压某条 entry 的 `FileOutputStream.use {}` 里抛了 `MAX_EXTRACT_BYTES` 触发的 IOException
（1031-1034），这条 entry 可能已经写了**部分**内容到磁盘。
catch (e: Exception) 里调 `cleanExtractionPartials` 清理了，
**但进度流没强制推到 (n, n) 的"已清理"态**。

UI 可能从「解压中 200/412」瞬间切到「Failed」，没一个明确的「已清理」过渡。

不致命，纯 UX 跳变。如果想做得更细，加一个 `Progress.CleaningUp` 中间态。

### 涉及文件
- `app/src/main/java/com/eareyereading/tts/EmbeddedTtsEngine.kt:851-868`（`countTarEntries`）
- `app/src/main/java/com/eareyereading/tts/EmbeddedTtsEngine.kt:967-980`（动态分母兜底）
- `app/src/main/java/com/eareyereading/tts/EmbeddedTtsEngine.kt:1007-1012`（解压循环过滤）

## 5. 阅读详情页：屏占比不足 + 操作栏常驻挤压阅读空间

### 现象
- 阅读详情页（`ReaderScreen`）顶部 TopAppBar + 底部 ReadingBottomBar **常驻显示**，
  把可阅读区域挤掉一大截。
- TopAppBar 高度本身约 64dp，叠加系统状态栏（约 24-30dp）后，顶部留白合计 ~90dp。
- BottomBar 含翻页 / 进度条，高度约 56-72dp；叠加系统导航栏后底部留白合计 ~80-100dp。
- 在主流 6.5-6.7 寸手机（屏幕高度 ~880dp）上，可阅读区域只剩 ~700dp，**有效屏占比不足 80%**。
- 长段落（4-5 行）滚动时，操作栏始终占据屏幕上下边缘，**没有任何"沉浸阅读"状态**。
- 用户期待：默认进入阅读态时只看到正文；**轻击空白区域显示/隐藏 TopAppBar + BottomBar**（类似 iBooks / 多看 / 微信读书 的"点击中央切换 chrome"交互）。

### 根因（代码定位）
- 文件：`app/src/main/java/com/eareyereading/ui/screens/reader/ReaderScreen.kt`
- `Scaffold` 始终以 `topBar` + `bottomBar` 形式挂载（113-262 行），没有 chrome 可见性状态。
- `Scaffold` 的 `contentWindowInsets` 没有显式设置，**默认让 TopAppBar/BottomBar 吃满系统状态栏 + 导航栏的高度**，
  又额外增加了一截系统 insets 的不可读区域。
- 段落实体（`LazyColumn`）被 `padding(horizontal = 20.dp)` 包裹（269 行），
  横向 20dp 边距对长段落阅读是合理的；**问题在垂直方向**：`padding(padding)` 用的是 Scaffold 内部 padding，
  等同于 topBar/bottomBar 的固定高度。
- 没有检测"轻击中央空白"的手势或点击监听器。

### 期望行为
1. **默认进入沉浸态**：进入阅读页时 TopAppBar + BottomBar **隐藏**，
   段落实体向上/向下扩展到屏幕真正可用区域。
2. **轻击空白切换 chrome**：
   - 点击段落**之间的空白**（不是段落文字本身，避免误触单词查询）切换 chrome 显隐。
   - 段落文字上的点击仍走现有的"选词 / 选句 / 翻页"逻辑，不受影响。
3. **过渡动画**：chrome 显/隐用 `AnimatedVisibility`（slideInVertically + fadeIn，约 200ms），
   不要瞬切。
4. **保留交互场景的 chrome**：以下场景应**始终显示** chrome 或显式重置为显示：
   - 滚动 LazyColumn 时短暂显示（scroll-driven reveal）。

## 6. EmbeddedTtsEngine — TTS 引擎真实 bug

### 6.1 [P0] AudioTrack buffer 小于设备最小值 → 长句静默丢失
- **文件**：`tts/EmbeddedTtsEngine.kt:1705-1722, 1731-1734`
- **现象**：长句（>2 秒朗读）的最后一个 chunk `track.write()` 返回 `ERROR_BAD_VALUE` (-22)，整段不发声，**doSpeakLocked 继续推进到下一句**。用户听到"句间停顿 1-2 秒 → 继续读下一句"，但没有任何报错提示。
- **根因**：`val bufferSize = pcm16.size * 2` 正好等于数据本身，没有富余；`MODE_STATIC` 模式要求 buffer ≥ `dataSize + 16KB 头部开销`。
- **修法**：
  ```kotlin
  val minBuffer = AudioTrack.getMinBufferSize(sampleRate, AudioFormat.CHANNEL_OUT_MONO, AudioFormat.ENCODING_PCM_16BIT)
  if (minBuffer <= 0) return
  val bufferSize = maxOf(pcm16.size * 2, minBuffer)
  ```

### 6.2 [P0] `$.50` / `$0.99` 读成 "dollars point fifty"
- **文件**：`tts/EmbeddedTtsEngine.kt:370-373, 380-387, 403`
- **现象**：`"It costs $.50"` → 朗读 *"It costs dollars point fifty"*；`"$10.5"` → *"ten dollars point five"*。整体含义被歪曲。
- **根因**：三个 regex 覆盖不严密：
  - L370 `\\$(\\d+)` 要求 `$` 后是完整整数 → `$.50` / `$0.99` 不匹配
  - L380 `(?<!\\d)(\\d+)(?!\\d|:)` 抓 `50`、`99` 走 `fifty` / `ninety-nine`
  - L403 `s.replace("$", " dollars ")` 把 `$` 换掉
  最终 `$.50` → ` dollars .fifty`。
- **修法**：L370 正则改为 `\\$(\\d+(?:\\.\\d+)?)`，替换 lambda 区分整数/小数（"X dollars Y cents" / "X dollars point Y"）。

### 6.3 [P0] fullStream 取消探测在最后 256KB 几乎不触发
- **文件**：`tts/EmbeddedTtsEngine.kt:1381-1384`
- **现象**：用户在 99% 进度离开页面，但下载继续跑完最后 1-2MB，最坏 ~2-10 秒才响应取消。
- **根因**：
  ```kotlin
  if (totalRead % 262144L < read) {
      ensureActive()
  }
  ```
  当 `read` 越来越小（最后一包 < 1KB），`totalRead % 262144L < read` 概率仅 ~0.4%，**最后 256KB 段大概率永远不调 `ensureActive()`**。`appendStream` 用 `sinceCheck` 累加器是 OK 的。
- **修法**：改用 `sinceCheck` 累加器（与 `appendStream` 一致）。

### 6.4 [P0] `conn?.inputStream != null` 探测副作用消费首字节 → 200/206 响应被截断
- **文件**：`tts/EmbeddedTtsEngine.kt:1225-1232`
- **现象**：间歇性 "connection reset by peer" 时 socket 未及时归还池；高并发（设置页 + 阅读页同时触发下载）下 `java.net.SocketException: No buffer space available`。
- **根因**：`conn?.inputStream != null` 的探测有副作用 —— 某些 server 在 `getInputStream()` 时立即开始读 socket buffer，**真正的 200/206 响应被提前消费了一小段**。后续 `streamResponse` 再 `conn.inputStream.use { ... }` 时剩余字节比预期少，**文件残缺**。解压 bzip2 报 "invalid header"，`cleanExtractionPartials` 清理掉所有产物，**用户重试仍失败**。
- **修法**：用 `responseCode in [200, 299] || 206` 作为判定（已在 `code` 变量），不再探测 `inputStream`。

### 6.5 [P1] `MODE_STATIC` 立即 release 导致句尾 100-200ms 截断
- **文件**：`tts/EmbeddedTtsEngine.kt:1687-1698, 1784-1790`
- **现象**：每句话尾音在元音中间被打断，连起来像"结巴"。
- **根因**：`playPcm` 用 `while (elapsed < durationMs) { delay(50); ... }` 估算时长；新 chunk 立即 `release()` 旧 track，但 `MODE_STATIC` 模式下 `release()` 会**强制终止**正在被硬件 buffer queue 消费的音频 → 丢尾部 sample。
- **修法**：用 `setNotificationMarkerPosition + OnPlaybackPositionUpdateListener` 取代 `while` 循环。

### 6.6 [P1] cancel 分支 + finally 双重 `disconnect()` 产生 logcat 噪声
- **文件**：`tts/EmbeddedTtsEngine.kt:1219-1232`
- **现象**：Android 13+ 偶发 `IllegalStateException: disconnect() called on already disconnected connection` 冒到 logcat 顶层。
- **根因**：L1220 cancel 分支已 `conn?.disconnect()`；L1231 finally 又调一次。
- **修法**：删 L1220，仅保留 finally 路径。

### 6.7 [P1] 状态写入耦合在 `speakMutex` 锁内
- **文件**：`tts/EmbeddedTtsEngine.kt:1404-1417`
- **现象**：状态/锁耦合反模式 —— `_state.value = EngineState.READY(modelInfo.id)` 在 `speakMutex` 锁内写，外层 collect 立即看到 READY，但 `speak()` 还没真正播放，**界面/状态与实际播放脱节**。
- **修法**：把 `_state.value = ...` 移到 `speakMutex.withLock` 块**外**。

### 6.8 [P1] 句子链无 buffer 间隔，AudioTrack 切换产生"啵"声
- **文件**：`util/TtsHelper.kt:167-183` + `EmbeddedTtsEngine.kt:1687-1726`
- **现象**：长段落（>10 句）后几句开始可听见"啵"声；logcat 偶现 `AudioTrack: AUDIO_OUTPUT_FLAG_FAST denied by client`。
- **根因**：`speak()` 完成后无 delay，下一句立刻 `playPcm` 抢占：旧 track 的 native buffer 还在被硬件消费 → 抢占冲突。
- **修法**：TtsHelper `speak()` 后加 `delay(20)`；或让 `speak()` 内部等 AudioTrack marker（见 6.5 修法）。

### 6.9 [P2] `preprocessForTts` 缩写无上下文，`CT scan` 误读 "Central Time scan"
- **文件**：`tts/EmbeddedTtsEngine.kt:454-465`
- **现象**：`"the CT scan"` → *"the Central Time scan"*；`"the MT route"` → *"the Mountain Time route"*。
- **根因**：`\\bCT\\b` / `\\bPT\\b` / `\\bMT\\b` / `\\bET\\b` 无上下文约束。
- **修法**：高频歧义缩写（CT/PT/MT/ET）需要 POS tagger 配合或显式词典（`PosTagger` 已 import 但未用）。

### 6.10 [P2] CancellationException 路径不删 tarball 残片
- **文件**：`tts/EmbeddedTtsEngine.kt:820-826`
- **现象**：下载 66MB 模型到一半关页面 → 残留几 MB 到几十 MB 不完整 tarball 永远占盘。
- **根因**：CancellationException 分支只 `cancelDownloadNotification` + 重置状态流，**没调 `cleanExtractionPartials` 清 tarball**。
- **修法**：L820-826 增加 `tarballFile.delete()` 和 `tarballComplete.delete()` 清理（调 `cleanExtractionPartials`）。

### 6.11 [P1] 内置 TTS 解压耗时过长 —— 多个可优化点
- **文件**：`tts/EmbeddedTtsEngine.kt:851-868, 947-1056, 262-266`
- **现象**：用户报告"内置模型下载后进行解压的过程耗时太长"
- 实测（Piper lessac-medium，66MB bz2 归档，解压后 ~66MB）：
  - **bzip2 解码**（CPU bound）：单线程 `BZip2CompressorInputStream`，中端机 1-2 秒、低端机 3-5 秒
  - **预扫**（`countTarEntries`，851-868 行）：**完整跑一遍 bzip2 + tar 解析但不写盘** —— 等价于把整个 bz2 解码两次（一次预扫 + 一次真实解压）
  - **真实解压 + 写盘**：单线程顺序 `FileOutputStream`，espeak-ng-data 几百个小文件每个都 open/close 一次
  - 总耗时：中端机 4-6 秒、低端机 8-15 秒
- 用户看着"解压中（统计文件数…）"不动（**没有 ETA 提示**），以为卡死

### 根因（代码定位）

#### 6.11.1 [P1] **bzip2 单线程解码**
- `EmbeddedTtsEngine.kt:990` `BZip2CompressorInputStream(fis).use {}` —— Apache Commons Compress 的 bzip2 解码器**单线程**
- 解压 66MB bz2（~10MB 压缩 → ~66MB 原始）在低端 CPU 上 3-5 秒
- **没有任何并行**（commons-compress 也提供 `BZip2CompressorInputStream` 单线程版）
- 选型上 Piper 归档天然是 bz2 压缩（k2-fsa 团队用 bz2 是历史选择），无法直接换格式

#### 6.11.2 [P1] **预扫把 bzip2 + tar 完整跑了一遍**
- `countTarEntries`（851-868 行）独立地把 `BZip2CompressorInputStream + TarArchiveInputStream` 跑一遍，**只数 entry 不写盘**
- 紧接着 947-1056 行真实解压**又**跑一遍同样的 bzip2 + tar 解析
- 整个 bz2 文件被 bzip2 解码**两次**，CPU 浪费 100%

#### 6.11.3 [P1] **写盘是单线程串行 + 每条 entry open/close**
- `FileOutputStream(outFile).use { out -> while (...) out.write(...) }`（1021-1043 行）
- espeak-ng-data 几百个小 entry（部分 < 1KB），每个都 syscall open/close
- 单线程顺序 IO，磁盘 IO 等待时 CPU 空转，CPU 解码时磁盘空转
- **没有 `BufferedOutputStream` 包裹**（FileOutputStream 内部 write 也是 native syscall，但 256KB buf 对小文件没意义）

#### 6.11.4 [P2] **`MAX_EXTRACT_BYTES = 512MB` 远超实际，余量浪费**
- `EmbeddedTtsEngine.kt:262-266` 注释说"正常 Piper 归档解压后 ~120MB，给 4 倍余量"
- 实际 Piper lessac-medium 解压后只有 **~66MB**（line 289 `约 66MB`）
- 120MB 这个数字已经偏大（4 倍余量 = 1+3 = 3 倍偏差），512MB 实际是 8 倍余量
- 不直接影响耗时，但 bzip2 流对超大归档会保持更多内存（解压输出缓冲）

#### 6.11.5 [P2] **进度显示"统计文件数…"阶段无 ETA**
- `downloadProgress.collect`（ReaderViewModel.kt:296-298）显示"解压中（统计文件数…）"
- 预扫 1-3 秒期间用户看不到任何数字跳动，**完全无 ETA**
- 真实解压时 `extractedEntries / totalEntries` 跳动快（几百 entry 在 1-2 秒内刷完），但**没有"剩余秒数"显示**

### 期望行为

#### 高 ROI 优化（必做）
1. **跳过预扫，直接动态分母**：
   - 去掉 `countTarEntries`（851-868）
   - 解压前先按 `modelInfo.sizeBytes * 1.5` 估算分母（解压后通常比 bz2 大 1.2-1.5x）
   - 解压中 `pushExtractionProgress` 已有的"动态分母"分支（967-970 行）走默认路径
   - 节省 ~50% CPU 时间（少跑一遍 bzip2 解码）
2. **bzip2 解压多线程**：
   - 切分 bz2 文件为多个块并发解码（commons-compress 不直接支持，需要换实现如 `aircompressor` / `jbzip2`）
   - **中等 ROI**：CPU 多核解压能提速 2-3x，但增加代码复杂度
3. **写盘异步 + 批量**：
   - 用 `BufferedOutputStream` + 8KB buf 包裹 `FileOutputStream`
   - 几百个 espeak-ng-data 小文件，**改用 `RandomAccessFile` 预分配空间 + 一次 fsync**
   - 或者：**把"读 bzip2 流"和"写文件"分开两个协程/线程**（生产者-消费者），磁盘 IO 等待时 CPU 继续解下一块
4. **进度条加 ETA**：
   - `extractionStartMs` 已有，添加 `currentSpeed = extractedBytes / elapsedSeconds`
   - UI 显示"剩余 ~Xs"
   - **低 ROI 改动**，纯 UX

#### 中 ROI 优化（可下迭代）
5. **缓存预扫结果到本地**：第一次解压后保存 `entries = 412` 到 `DataStore`，下次升级/重装跳过预扫
6. **不预先解压整个 bz2**：流式 lazy read，按需展开 entry（但 sherpa-onnx 需要整个 model.onnx 文件就绪才能 load，无法流式）
7. **换更快的压缩格式**：gzip / zstd（比 bzip2 快 5-10x），但需要 k2-fsa 团队配合重新打包 Piper 归档

## 63. [产品决策] 移除"清除缓存"功能

### 决策
- **直接砍掉**设置页"数据"卡片里的"清除缓存"按钮及对应逻辑
- 包括：
  - `uiState.isClearing` / `uiState.cacheSizeMb` 字段
  - `SettingsViewModel.clearCache()` 方法
  - `SettingsViewModel.refreshCacheSize()` 方法
  - "清除缓存" SettingRow UI（SettingsScreen.kt:1015-1025 区域）
  - `AndroidManifest.xml` 无相关权限需要清理

### 功能现状（移除前）
- `ui/screens/settings/SettingsScreen.kt:1015-1025`：
  ```kotlin
  SettingRowClickable(
      icon = Icons.Default.Delete,
      iconBg = ErrorBg,
      iconColor = Error,
      title = "清除缓存",
      subtitle = if (uiState.isClearing) "清除中..." else {
          String.format(java.util.Locale.getDefault(), "%.1f MB", uiState.cacheSizeMb)
      },
      onClick = { viewModel.clearCache() },
  )
  ```
- `viewModel.clearCache()`（行 584-599）：
  ```kotlin
  fun clearCache() {
      viewModelScope.launch {
          _uiState.update { it.copy(isClearing = true) }
          try {
              // 清理缓存目录（临时文件等）；导出备份不在 cacheDir，不受影响。
              withContext(Dispatchers.IO) {
                  context.cacheDir.walkTopDown().forEach { it.delete() }
              }
              _uiState.update { it.copy(isClearing = false, snackbarMessage = "缓存已清除") }
          } catch (e: kotlinx.coroutines.CancellationException) {
              throw e
          } catch (e: Exception) {
              _uiState.update { it.copy(isClearing = false, snackbarMessage = "清除失败: ${e.message}") }
          }
          refreshCacheSize()
      }
  }
  ```
- `refreshCacheSize()`（行 305-316）启动时 + 清完后异步统计 cacheDir 占用

### 移除原因（产品角度）
1. **系统已有同样功能**：Android 系统设置 → 应用信息 → 存储 → 清除缓存，一键可达
2. **误删风险大**：当前 `cacheDir.walkTopDown().forEach { it.delete() }` **递归删除整个 cacheDir**，包含：
   - WebView 缓存
   - OkHttp 缓存（如果未来引入）
   - ML Kit 翻译模型的临时文件
   - 第三方库的临时文件
   - **没有确认弹窗**，一键删光无法撤销
3. **与"导出数据"功能冲突**：旧实现把导出备份放 `cacheDir`，用户点"清除缓存"会把唯一备份删了（line 451 注释已记录）。**虽然现在已迁到 externalFilesDir**，但 cacheDir 仍有其他潜在文件
4. **用户不期望"清除缓存"=删光所有**：微信/QQ 那种"清除缓存"是清聊天图片/视频，不是删系统级缓存。语义错位
5. **代码上多余**：Android 系统会按需自动清理 cacheDir（空间不足时），app 自己再加一个功能收益小
6. **没有"清除成功"的可观反馈**：用户点完按钮只看到 snackbar "缓存已清除"，但没看到释放了多少空间、删了哪些类型文件，体验上"按了一下没动静"

### 移除范围（明确）
- **要删**：
  - `SettingsScreen.kt:1015-1025` "清除缓存" SettingRow（含 `SettingRowClickable` 调用）
  - `SettingsViewModel.kt` `clearCache()` 方法
  - `SettingsViewModel.kt` `refreshCacheSize()` 方法
  - `SettingsViewModel.kt` `isClearing` / `cacheSizeMb` 字段
  - `SettingsUiState.kt` `isClearing` / `cacheSizeMb` 字段
  - SettingsScreen 里所有 `uiState.isClearing` / `uiState.cacheSizeMb` 引用
- **要保留**：
  - `cacheDir` 本身（其他功能可能还在用，如 line 681 `tempFile = File(context.cacheDir, "import_temp.json")`）
  - "导出数据" / "导入数据" 功能
  - "删除语音模型" 功能（在 63 节范围之外，且产品需要）
- **不涉及**：
  - `AndroidManifest.xml`（清除缓存不需要权限）
  - 其他 cacheDir 用户（如 line 451 注释提到的导出备份历史位置）

### 涉及文件
- `app/src/main/java/com/eareyereading/ui/screens/settings/SettingsScreen.kt:305-316, 584-599, 1015-1025`（删除 / 修改）
