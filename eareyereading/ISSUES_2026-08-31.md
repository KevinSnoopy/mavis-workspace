## 1. 设置页"内置 TTS 模型"下载阶段

### 1.1 [P0] 解压阶段仍硬编码显示"正在下载…请保持网络连接"
- **文件**：`ui/screens/settings/SettingsScreen.kt:905-912`
- **现象**：下载完成进入解压阶段后，卡片**内部**进度条正确显示"解压中 (xxx/yyy)"，但卡片**底部**的 SettingRow 仍硬编码显示"正在下载…请保持网络连接"。整张卡片同时给用户"在下载"和"在解压"两个互相矛盾的信号。
- **根因**：905-912 行 SettingRow 没接 `embeddedDownloadStage`，也没区分 `Extracting` 阶段。
- **影响**：阅读页弹窗 `ReaderScreen.kt:494-495` 也有同款 fallback 文案，阶段切换瞬间可能闪过"请保持网络"。
- **修法**：根据 `embeddedDownloadStage` / `embeddedInitializing` 分别显示"正在解压" / "正在初始化"，subtitle 改为"无需联网"或留空；阅读页 fallback 改为只在 Downloading 时使用。
- **涉及文件**：
  - `ui/screens/settings/SettingsScreen.kt:905-912`
  - `ui/screens/reader/ReaderScreen.kt:494-495`

### 1.2 [P0] 解压时文件数量统计预扫分母 bug（5 条子 bug）
- **文件**：`tts/EmbeddedTtsEngine.kt:851-868, 947-1056`
- **现象**：解压 Piper 归档时进度条可能永远到不了 100%，停滞在 99.x%。
- **根因**：`countTarEntries`（851-868）把所有 entry 都 +1；解压循环（1007-1012）只数 `isFile || isDirectory`，跳过 symlink。归档里有 symlink（`espeak-ng-data/phonindex`）时分母 > 分子。
- **5 条子 bug**：
  1. **Bug 1 P0**：预扫/解压过滤口径不一致 → 进度卡 99%
  2. **Bug 2 P2**：预扫无路径校验（与 Bug 1 配对）
  3. **Bug 3 P2**：目录条目计入"文件数"，UI 体感偏差
  4. **Bug 4 P1**：预扫失败时末态分子分母差 1，UI 不收敛
  5. **Bug 5 P3**：异常态 UX 跳变（无 `CleaningUp` 中间态）
- **修法**：抽 `shouldCountTarEntry(entry, canonicalRoot): Boolean` 私有函数，预扫与解压循环共用；末态分子分母对齐；加 CleaningUp 态。
- **涉及文件**：`tts/EmbeddedTtsEngine.kt:851-868, 967-980, 1007-1012, 1045-1052`

### 1.3 [P1] TTS 解压耗时过长（5 个可优化点）
- **文件**：`tts/EmbeddedTtsEngine.kt:851-868, 947-1056, 262-266`
- **现象**：Piper 66MB bz2 归档解压总耗时中端机 4-6 秒、低端机 8-15 秒，用户看着"统计文件数…"不动以为卡死。
- **根因**：
  1. `countTarEntries` 完整跑一遍 bzip2 + tar（不写盘）—— **bzip2 被解码两次**
  2. `BZip2CompressorInputStream` 单线程
  3. 文件写盘单线程 `FileOutputStream` 串行
  4. `MAX_EXTRACT_BYTES = 512MB` 远超实际（66MB Piper 实际只有 8 倍余量）
  5. "统计文件数…"阶段无 ETA
- **修法**：
  1. **去掉预扫**，用 `modelInfo.sizeBytes * 1.5` 估算分母 → 立省 50% CPU
  2. bzip2 多线程（换 `aircompressor` / `jbzip2` 依赖）→ 提速 2-3×
  3. `BufferedOutputStream` + 8KB buf，espeak-ng-data 用 `RandomAccessFile` 预分配
  4. `MAX_EXTRACT_BYTES` 改 256MB
  5. UI 加 ETA 提示
- **涉及文件**：`tts/EmbeddedTtsEngine.kt:851-868, 262-266, 1015-1043`；`ui/screens/reader/ReaderViewModel.kt:295-298`

## 2. TTS 引擎（EmbeddedTtsEngine / TtsHelper / CollinsClassifier）

### 2.1 [P0] AudioTrack buffer 小于设备最小值 → 长句静默丢失
- **文件**：`tts/EmbeddedTtsEngine.kt:1705-1722, 1731-1734`
- **现象**：长句（>2 秒朗读）最后一个 chunk `track.write()` 返回 -22，整段不发声，**doSpeakLocked 继续推进到下一句**。用户听到"句间停顿 1-2 秒 → 继续读下一句"，无任何提示。
- **根因**：`val bufferSize = pcm16.size * 2` 正好等于数据本身，`MODE_STATIC` 要求 buffer ≥ `dataSize + 16KB 头部开销`。
- **修法**：`val minBuffer = AudioTrack.getMinBufferSize(...); val bufferSize = maxOf(pcm16.size * 2, minBuffer)`

### 2.2 [P0] `$.50` / `$0.99` 读成 "dollars point fifty"
- **文件**：`tts/EmbeddedTtsEngine.kt:370-373, 380-387, 403`
- **现象**：`"It costs $.50"` → *"It costs dollars point fifty"*；`"$10.5"` → *"ten dollars point five"*。
- **根因**：三个 regex 覆盖不严密。L370 `\\$(\\d+)` 要求 `$` 后是完整整数 → `$.50` / `$0.99` 不匹配；L380 抓 `50` / `99` 走 `fifty` / `ninety-nine`。
- **修法**：L370 正则改为 `\\$(\\d+(?:\\.\\d+)?)`，替换 lambda 区分整数/小数（"X dollars Y cents"）。

### 2.3 [P0] fullStream 取消探测在最后 256KB 几乎不触发
- **文件**：`tts/EmbeddedTtsEngine.kt:1381-1384`
- **现象**：用户在 99% 进度离开页面，下载继续跑完最后 1-2MB，最坏 ~2-10 秒才响应取消。
- **根因**：`if (totalRead % 262144L < read) ensureActive()` 当 `read` 越来越小（最后一包 < 1KB）时概率仅 ~0.4%，最后 256KB 段大概率永远不调。
- **修法**：改用 `sinceCheck` 累加器（与 `appendStream` 一致）。

### 2.4 [P0] `conn?.inputStream != null` 探测副作用消费首字节
- **文件**：`tts/EmbeddedTtsEngine.kt:1225-1232`
- **现象**：高并发（设置页 + 阅读页同时触发下载）下 `SocketException: No buffer space available`；解压时 bzip2 报 "invalid header"，**用户重试仍失败**。
- **根因**：`conn?.inputStream != null` 探测有副作用 —— 某些 server 在 `getInputStream()` 时立即开始读 socket buffer，**真正的 200/206 响应被提前消费了一小段**。后续 `streamResponse` 再 `conn.inputStream.use { ... }` 时剩余字节比预期少，文件残缺。
- **修法**：用 `responseCode in [200, 299] || 206` 作为判定（已在 `code` 变量），不再探测 `inputStream`。

### 2.5 [P1] `MODE_STATIC` 立即 release 导致句尾 100-200ms 截断
- **文件**：`tts/EmbeddedTtsEngine.kt:1687-1698, 1784-1790`
- **现象**：每句话尾音在元音中间被打断，连起来像"结巴"。
- **根因**：`playPcm` 用 `while (elapsed < durationMs) { delay(50) }` 估算时长；新 chunk 立即 `release()` 旧 track，但 `MODE_STATIC` 下 `release()` 会强制终止正在被硬件 buffer queue 消费的音频。
- **修法**：`setNotificationMarkerPosition + OnPlaybackPositionUpdateListener` 取代 `while` 循环。

### 2.6 [P1] cancel 分支 + finally 双重 `disconnect()` 产生 logcat 噪声
- **文件**：`tts/EmbeddedTtsEngine.kt:1219-1232`
- **根因**：L1220 cancel 分支已 `disconnect()`；L1231 finally 又调一次。
- **修法**：删 L1220，仅保留 finally 路径。

### 2.7 [P1] 状态写入耦合在 `speakMutex` 锁内
- **文件**：`tts/EmbeddedTtsEngine.kt:1404-1417`
- **现象**：状态/锁耦合反模式，**界面/状态与实际播放脱节**。
- **修法**：把 `_state.value = EngineState.READY(...)` 移到 `speakMutex.withLock` 块**外**。

### 2.8 [P1] 句子链无 buffer 间隔，AudioTrack 切换产生"啵"声
- **文件**：`util/TtsHelper.kt:167-183`
- **现象**：长段落后几句开始可听见"啵"声；logcat 偶现 `AudioTrack: AUDIO_OUTPUT_FLAG_FAST denied`。
- **修法**：TtsHelper `speak()` 后加 `delay(20)`，或让 `speak()` 内部等 AudioTrack marker。

### 2.9 [P1] CancellationException 路径不删 tarball 残片
- **文件**：`tts/EmbeddedTtsEngine.kt:820-826`
- **根因**：CancellationException 分支只重置状态流，没调 `cleanExtractionPartials` 清 tarball。
- **修法**：L820-826 增加 `tarballFile.delete()` / `tarballComplete.delete()`。

### 2.10 [P2] `preprocessForTts` 缩写无上下文，`CT scan` 误读 "Central Time scan"
- **文件**：`tts/EmbeddedTtsEngine.kt:454-465`
- **修法**：高频歧义缩写（CT/PT/MT/ET）需要 POS tagger 配合（`PosTagger` 已 import 但未用）。

### 2.11 [P2] TtsHelper.speak cancel + launch 竞态
- **文件**：`util/TtsHelper.kt:138-139`
- **根因**：`cancel()` 非阻塞，旧协程还在取消中，新协程立即 `scope.launch`，两个 `speak` 协程几乎同时跑。
- **修法**：用 `Job.cancelAndJoin()` 等旧协程退出再 launch；或 `EmbeddedTtsEngine.speak` 入口加 `ensureActive()`。

### 2.12 [P2] CollinsClassifier 排除单字母词，`"I"` 误判 UNKNOWN
- **文件**：`util/CollinsClassifier.kt:2257`
- **根因**：`if (w.length < 2) return WordLevel.UNKNOWN` 过严，但 `collinsOne` 包含 `"a", "i"`。
- **修法**：`if (w.length < 2) return if (w in collinsOneLower) WordLevel.CORE else WordLevel.UNKNOWN`

### 11.1 [P0] SM-2 算法 `easeFactor` 无上限 + 整数溢出 → 单词永久消失或永久 due
